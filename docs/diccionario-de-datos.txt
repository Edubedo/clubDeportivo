====================================================================================================
1. CÓMO LEER ESTE DOCUMENTO
====================================================================================================

Firestore no tiene tablas ni columnas: guarda DOCUMENTOS (conjuntos de campos) dentro de COLECCIONES.
Este diccionario describe cada colección como si fuera una tabla:

  Campo        Nombre exacto del campo dentro del documento.
  Tipo         String, Number, Boolean, Timestamp, Array<String>, Map.
  Req          S = el campo siempre existe en documentos nuevos.
               N = es opcional: puede no existir (se indica cuándo).
  Descripción  Qué guarda y qué valores admite.

"PK" es el id del documento. "FK" es un campo que guarda el id de un documento de OTRA colección
(Firestore NO valida ni hace cumplir estas referencias: lo hace la aplicación).

Cada colección indica también:
  Escribe / Lee : qué parte de la app la usa hoy.
  Observado     : cuántos documentos tenía la base el 2026-09-30 (puede haber cambiado).
  OBSOLETOS     : campos heredados de estructuras anteriores. Siguen en los documentos viejos y la app
                  los sabe leer, pero ya no se escriben. Se pueden borrar cuando todo el equipo use
                  la versión actual de la app.


====================================================================================================
2. CONVENCIONES DE DISEÑO
====================================================================================================

Nombres
  - Colecciones en plural y camelCase (membresias, inscripcionesTorneo).
  - Campos en camelCase y en español (fechaInicio, cupoMaximo). Sin abreviaturas.
  - Un mismo concepto se llama igual en todas las colecciones: areaId, usuarioId, membresiaId,
    reservaId, torneoId, herramientaId siempre son referencias; xxxNombre es el nombre copiado.

Identificadores (PK)
  - Por omisión, id automático de Firestore (20 caracteres).
  - Excepciones con significado, para impedir duplicados:
      usuarios/{uid}                       uid que entrega Firebase Authentication.
      miembros/{codigo}                    el código de miembro (CLB-XXXXXX) es el id: no puede repetirse.
      inscripcionesTorneo/{torneoId}_{usuarioId}   una persona no se inscribe dos veces al mismo torneo.
      restriccionesHorario/rh-{areaId}     un horario general por área.
      precios/{clave}                      INDIVIDUAL_NORMAL, FAMILIAR_1, VISITA...
  - El id NO se repite dentro del documento (antes usuarios guardaba un campo "id": ya se quitó).

Fechas y horas
  - Fecha de negocio : String "yyyy-MM-dd"        (fecha de una reserva, vigencia de una membresía).
  - Hora de negocio  : String "HH:mm", 24 horas   (horaInicio, horaFin, horaApertura).
    Se guardan como texto porque así se ordenan y comparan correctamente sin depender de zonas horarias.
  - Momento exacto (auditoría): Timestamp de Firestore (creadoEn, actualizadoEn), puesto por el servidor.
  - Excepción: checkins.fechaHora es String ISO "yyyy-MM-ddTHH:mm:ss" (ver 4.11).

Valores con opciones fijas
  - Se guardan como String en MAYÚSCULAS sin espacios (ACTIVA, PENDIENTE_APROBACION). Ver sección 5.

Dinero
  - Number (double) en pesos mexicanos. El campo "moneda" ("MXN") acompaña a pagos y precios.

Auditoría
  - creadoEn / actualizadoEn (Timestamp) en todos los documentos que crea la app desde esta versión.
  - creadoPor / actualizadoPor (uid) donde importa saber quién lo hizo: membresias, torneos, precios.
  - Los documentos anteriores a la versión 3 pueden no tener estos campos (no se inventan fechas).

Desnormalización (copiar un dato para no tener que buscarlo)
  - En NoSQL no hay JOIN. Para mostrar una lista sin hacer una lectura extra por fila, se copia el
    NOMBRE del documento referenciado junto a su id:
      reservas.areaNombre / usuarioNombre / deporte        torneos.areaNombre
      membresias.titularNombre / titularCodigo             inscripcionesTorneo.torneoNombre / usuarioNombre
      materialAsignado.herramientaNombre
  - En reservas, pagos e inscripciones la copia es a propósito HISTÓRICA: si el área se renombra o se
    elimina, el registro sigue diciendo lo que decía cuando ocurrió.
  - En torneos la copia puede quedar desactualizada si se renombra el área; se corrige la
    siguiente vez que se guarda el registro. El id (areaId) es siempre la fuente de verdad.

Contadores
  - torneos.inscritos y membresias.totalPersonas son contadores guardados en el documento. Se cambian en
    la misma operación que crea o quita el registro relacionado (transacción o lote), así no se cuenta
    cada vez y no se desfasan.


====================================================================================================
3. MAPA DE RELACIONES
====================================================================================================

  Lectura: A --< B  significa "un documento de A se relaciona con MUCHOS de B" (B guarda el id de A).

  Firebase Authentication (uid)
        |
        |  el uid es el id de
        v
   usuarios ---------------------------------------------------------------+
     | 1                                                                     |
     |                                                                       |
     |--< miembros (usuarioId)                                               |
     |        ^                                                              |
     |        | membresiaId                                                  |
     |        |                                                              |
     |   membresias (usuarioId = titular) --< integrantesFamiliares (OBSOLETA)
     |        |                                                              |
     |        +--< pagos (membresiaId, usuarioId)                            |
     |                                                                       |
     |--< reservas (usuarioId) >-- 1 areas (areaId)                          |
     |        |                                                              |
     |        +--< materialAsignado (reservaId) >-- 1 herramientas           |
     |        +--< checkins (reservaId)                                      |
     |                                                                       |
     |--< inscripcionesTorneo (usuarioId) >-- 1 torneos (torneoId) >-- 1 areas
     |                                                                       |
     +--< notificaciones (usuarioId)                                         |
                                                                             |
   areas --< restriccionesHorario (areaId)        herramientas (areaIds[]) >-- N areas
   precios, config: no dependen de otras colecciones.

  Cardinalidades importantes
    - Una membresía tiene 1 titular y, si es FAMILIAR, hasta (maxIntegrantes - 1) integrantes más.
      Cada persona es un documento en miembros con su propio código y su propia cuenta de acceso.
    - Una herramienta se usa en VARIAS áreas del mismo deporte (por eso areaIds es un arreglo).
    - Un torneo ocupa UN área durante un rango de fechas y horas.

----------------------------------------------------------------------------------------------------
4.1  usuarios
----------------------------------------------------------------------------------------------------
Perfil de cada persona que tiene acceso al sistema (personal, socios, visitantes).
PK : uid de Firebase Authentication.
Escribe : FirebaseAuthRepository (registro), FirebaseGestionMembresiasRepository (miembros con código),
          PersonalRepository (alta/edición de personal), FirebaseUsuarioRepository (cambio de nombre).
Lee     : login, perfil, Personal, Membresías.
Observado: 12 documentos.

  Un solo documento por persona, para TODOS los tipos (personal, socios, visitantes). Los campos se agrupan
  por quién los usa; "Req" dice si siempre existen (S) o solo en ese tipo de persona (N).

  Campo          Tipo       Req  Descripción
  -------------- ---------- ---- --------------------------------------------------------------------
  -- Identidad y acceso (todos) --
  nombre         String     S    Nombre completo.
  email          String     S    Correo de la cuenta. Personal y registros normales: correo real. Miembros con
                                 código: correo interno derivado del código (clb-xxxxxx@miembros.clubdeportivo.app).
  telefono       String     S    Teléfono; "" si no se capturó.
  rol            String     S    SUPERADMIN | ADMIN | ADMIN_AREA | AYUDANTE_AREA | SOCIO | VISITANTE_EXTERNO.
                                 Si faltara, la app asume SOCIO. Personal: ADMIN (Administrador) o
                                 AYUDANTE_AREA (Encargado de área).
  estado         String     S    ACTIVO | INACTIVO. Inactivo = no puede iniciar sesión.
  fotoUrl        String     N    Ruta o URL de la foto de perfil.
  fechaRegistro  String     N    Fecha de alta de la cuenta (yyyy-MM-dd).
  creadoEn       Timestamp  N    Cuándo se creó el documento.
  actualizadoEn  Timestamp  N    Última modificación.
  -- Solo personal (rol ADMIN / AYUDANTE_AREA). Siempre presentes en ellos; "" si aún no se capturan --
  tipoPersonal   String     N    Tipo de trabajo: "Instructor" (por ahora el único que se da de alta).
  turno          String     N    Matutino | Vespertino.
  areaTrabajo    String     N    Área del club donde trabaja (deporte: "Fútbol", "Tenis"...). "" = sin área.
  fechaIngreso   String     N    Fecha en que entró como personal (yyyy-MM-dd).
  creadoPor      String     N    uid del administrador que lo dio de alta.
  -- Solo socios y visitantes con código --
  codigoMiembro  String     N    Código CLB-XXXXXX. Solo existe en cuentas creadas al registrar un miembro.

  OBSOLETOS:  correo  -> reemplazado por email.
              codigo  -> reemplazado por codigoMiembro.
              id      -> ya eliminado (repetía el id del documento).
  Nota: el personal se da de alta desde la pantalla Personal (solo administradores): se crea la cuenta en
        Firebase Authentication (correo + contraseña) y este documento con el mismo uid. La contraseña no se
        guarda en Firestore; para cambiarla se envía un correo de restablecimiento. Una persona INACTIVA no
        puede iniciar sesión.

4.3  miembros
----------------------------------------------------------------------------------------------------
Cada PERSONA cubierta por una membresía (el titular y cada integrante de un paquete familiar). Tiene su
propio código y con él entra al sistema.
PK : código de miembro, formato CLB- + 6 caracteres (A-Z sin I,L,O y 2-9). Ejemplo: CLB-DBWC3H.
     Como el código ES el id, Firestore garantiza que no se repita.
FK : membresiaId -> membresias ; usuarioId -> usuarios (su cuenta de acceso).
Escribe : FirebaseGestionMembresiasRepository.   Lee : login por código, Membresías, dashboard.
Observado: 1 documento.

  Campo          Tipo       Req  Descripción
  -------------- ---------- ---- --------------------------------------------------------------------
  nombre         String     S    Nombre completo.
  telefono       String     S    Teléfono de contacto; "" si no se capturó.
  correo         String     S    Correo de CONTACTO (no es el de acceso); "" si no se capturó.
  membresiaId    String     S    FK a membresias.
  parentesco     String     S    "Titular" o el parentesco con el titular (Cónyuge, Hijo, Integrante...).
  esTitular      Boolean    S    true solo para el titular de la membresía.
  usuarioId      String     S    FK a usuarios (uid de su cuenta en Authentication).
  fechaRegistro  String     S    Fecha de alta (yyyy-MM-dd).
  creadoEn       Timestamp  N    Alta del registro.
  actualizadoEn  Timestamp  N    Última modificación.

  Regla: quitar a un integrante de la membresía BORRA su documento aquí y marca su usuario INACTIVO; sin
         este documento su código deja de entrar.

  ultimaRenovacion   String     N    Fecha de la última renovación.
  creadoPor          String     N    uid de quien la registró.
  creadoEn           Timestamp  N    Alta del registro.
  actualizadoEn      Timestamp  N    Última modificación.

4.8  reservas
----------------------------------------------------------------------------------------------------
Uso de un área por una persona en una fecha y un rango de horas.
PK : id automático.   FK : usuarioId -> usuarios ; areaId -> areas.
Escribe : FirebaseReservaRepository.   Lee : Reservas, Áreas (reservas de hoy), dashboard, cupo.
Observado: 7 documentos (2 de áreas que ya se eliminaron: conservan su deporte y nombre copiados).

  Campo            Tipo       Req  Descripción
  ---------------- ---------- ---- --------------------------------------------------------------------
  usuarioId        String     S    FK a usuarios. Quien reserva.
  usuarioNombre    String     S    Nombre de quien reserva (copia histórica).
  areaId           String     S    FK a areas.
  areaNombre       String     S    Nombre del área al momento de reservar (copia histórica).
  deporte          String     S    Deporte del área (copia histórica).
  fecha            String     S    Día de la reserva (yyyy-MM-dd).
  horaInicio       String     S    "HH:mm" (siempre en punto).
  horaFin          String     S    "HH:mm"; posterior a horaInicio. Máximo 4 horas.
  duracionHoras    Number     S    horaFin - horaInicio, en horas.
  personas         Number     S    Lugares del cupo del área que ocupa (mínimo 1).
  estado           String     S    CONFIRMADA | PENDIENTE_APROBACION | CANCELADA | FINALIZADA.
  esExterno        Boolean    S    true si la hizo un visitante externo (nace PENDIENTE_APROBACION).
  canceladaEn      Timestamp  N    Cuándo se canceló. Solo si estado = CANCELADA.
  sinPenalizacion  Boolean    N    true si se canceló con 4 horas o más de anticipación. Solo si CANCELADA.
  creadoEn         Timestamp  N    Alta del registro.
  actualizadoEn    Timestamp  N    Última modificación.

  Regla de cupo: por cada hora, la suma de "personas" de las reservas CONFIRMADA o PENDIENTE_APROBACION
  no puede pasar de areas.capacidad; y en las horas de un torneo del área no entra ninguna reserva.

  areaId         String     S    FK a areas.
  areaNombre     String     S    Nombre del área (copia).
  fechaInicio    String     S    Primer día (yyyy-MM-dd).
  fechaFin       String     S    Último día; no anterior a fechaInicio.
  horaInicio     String     N    "HH:mm". Con horaFin define el horario de CADA día del rango.
  horaFin        String     N    "HH:mm". Si faltan las dos horas el torneo ocupa el día completo.
  cupoMaximo     Number     S    Participantes permitidos.
  inscritos      Number     S    Contador de inscripciones CONFIRMADAS (0 <= inscritos <= cupoMaximo).
  creadoPor      String     N    uid de quien lo creó.
  creadoEn       Timestamp  N    Alta del registro.
  actualizadoEn  Timestamp  N    Última modificación.

4.15  inscripcionesTorneo

Escribe : FirebaseTorneoRepository.inscribirse (transacción: valida cupo y duplicado y sube torneos.inscritos).
Lee : recuento de inscritos de torneos anteriores al contador.

  usuarioNombre     String     S    Nombre de la persona (copia histórica).
  fechaInscripcion  String     S    Día de inscripción (yyyy-MM-dd).

4.16  areas

Lee     : Áreas, Reservas, Torneos, Personal, dashboard.

  Campo            Tipo       Req  Descripción

6. ÍNDICES Y CONSULTAS
====================================================================================================

Todas las consultas de la app son de IGUALDAD sobre un solo campo, por lo que Firestore las resuelve con
sus índices automáticos: NO hace falta crear índices compuestos.

  Colección              Consulta                                   Para qué
  ---------------------- ------------------------------------------ -------------------------------------
  reservas               areaId ==                                  cupo y torneos de un área
  reservas               usuarioId ==                               reservas de una persona, límite de 3
  membresias             usuarioId ==                               membresía de una persona
  miembros               membresiaId ==                             personas de una membresía
  miembros               usuarioId ==  (limit 1)                    membresía de un integrante
  inscripcionesTorneo    torneoId ==  (conteo)                      torneos sin contador
  materialAsignado       reservaId ==                               material de una reserva
  restriccionesHorario   areaId ==                                  borrar el horario de un área
  integrantesFamiliares  membresiaId ==                             membresías anteriores a los códigos

Por documento: lecturas directas por id (usuarios, miembros, membresias, areas, torneos, herramientas).
Si más adelante se filtra en el servidor por área Y fecha a la vez (reservas de un día), hará falta un
índice compuesto reservas(areaId, fecha); Firestore muestra el enlace para crearlo en el primer intento.


====================================================================================================
7. REGLAS DE NEGOCIO QUE DEPENDEN DE LOS DATOS
====================================================================================================

  Acceso por código     Solo entra con el código quien tiene miembros/{codigo} y una membresía ACTIVA con
                        fechaVencimiento >= hoy. Suspender o vencer la membresía bloquea a TODAS sus personas.
  Cupo de reservas      Por hora: sum(reservas.personas vigentes) <= areas.capacidad.
  Reserva y torneo      Un torneo bloquea su área en sus horas; un torneo no puede crearse sobre reservas
                        vigentes ni sobre otro torneo del mismo área y horario.
  Reservas por socio    Máximo 3 reservas activas; 2 horas de anticipación mínima; 7 días como máximo hacia
                        adelante; cancelar sin penalización con 4 horas o más. El personal no tiene el límite.
  Torneo e inscripción  Una inscripción por persona y torneo; torneos.inscritos nunca pasa de cupoMaximo
                        (se valida en una transacción).
  Renovación            Suma un mes desde el vencimiento (si sigue vigente) o desde hoy (si ya venció).
  Precios               El precio de una membresía es el vigente al registrarla o renovarla.


====================================================================================================
8. SEGURIDAD
====================================================================================================

Las reglas están en `firestore.rules` (raíz del repo). Firebase no las toma del repo: se pegan en
Firebase console > Firestore > Reglas y se publican. Resumen:

  Roles      Administrador (SUPERADMIN, ADMIN) | Encargado de área (AYUDANTE_AREA, ADMIN_AREA heredado) |
             Socio | Visitante externo. Una cuenta con estado INACTIVO pierde los permisos del personal.
  usuarios   Leer: la propia cuenta y el personal. Crear: registro propio (solo Socio/Visitante), un
             administrador (cualquier rol) o el personal (solo clientes con código). Editar: cada quien su
             nombre/teléfono/foto, NUNCA su rol ni estado; el personal edita clientes; el personal del club
             solo lo edita un administrador. Borrar: administrador.
  miembros, membresias, integrantesFamiliares, pagos, precios
             Escribir: personal. Leer: personal y la persona dueña (titular o cubierta por la membresía);
             precios e integrantesFamiliares los lee cualquier sesión.
  areas, herramientas, torneos
             Leer: cualquier sesión. Escribir: personal (los torneos también suben `inscritos` al inscribirse,
             sin pasar de cupoMaximo).
  reservas   Leer: cualquier sesión (el cupo se calcula con las de todos). Crear: personal o la propia persona
             (un visitante externo siempre PENDIENTE_APROBACION). Quien reserva solo puede cancelar la suya.
  inscripcionesTorneo, materialAsignado
             Se crean a nombre de la propia persona (o el personal); el resto lo cambia el personal.
  config     Solo administrador (la migración de esquema).
  restriccionesHorario, checkins, notificaciones: personal (los dos últimos también los lee su dueño).
  Todo lo demás: denegado.

Campos que las reglas necesitan: usuarios.rol (si falta, la persona cuenta como Socio y no tiene permisos de
personal), usuarios.estado, usuarios.codigoMiembro (miembros con código), miembros.usuarioId, membresias.usuarioId,
reservas.usuarioId, inscripcionesTorneo.usuarioId y torneoId, torneos.cupoMaximo e inscritos.


====================================================================================================
9. PENDIENTES Y LIMITACIONES CONOCIDAS
====================================================================================================

  1. PAGOS no se registran. Registrar o renovar una membresía no crea un documento en pagos, así que el
     club no tiene historial de cobros. Falta elegir método de pago en los formularios y escribirlo.
  2. PERSONAL anterior a la versión 4 puede no tener cuenta de acceso (se creó solo el perfil). Para esas
     personas, "Enviar correo para cambiarla" avisa que no hay cuenta; hay que darlas de alta de nuevo con otro
     correo o crearles la cuenta a mano en Firebase Authentication con el uid del documento.
  3. INVENTARIO en memoria. La pantalla Inventario no usa la colección herramientas; sus datos se pierden
     al cerrar la app. Es la conexión más natural pendiente.
  4. HERRAMIENTAS sin descuento. Al asignar material a una reserva no baja cantidadDisponible.
  5. HORARIOS por deporte. restriccionesHorario no se lee; los horarios salen del código. Un deporte nuevo
     usa el horario por omisión (08:00 a 20:00).
  6. CHECKINS y NOTIFICACIONES sin pantalla ni escritura todavía.
  7. NOMBRES COPIADOS. torneos.areaNombre no se actualizan si se renombra un área.
  8. INTEGRANTES anteriores. Las membresías creadas antes de los códigos no tienen miembros con código; se
     pueden renovar, suspender y cambiar de plan, pero sus personas no se editan hasta volver a registrarlas.
  9. CAMPOS OBSOLETOS. Siguen en los documentos viejos (correo, codigo, areaId, tipoTurno, leido,
     fechaEnvio, diaSemana, horaInicio/horaFin de restricciones, actualizado). Se dejaron para no romper
     las ramas del equipo que aún los leen; se pueden borrar cuando todas usen la versión actual.
